# Архитектура RISC-V

## Среда для разработки под RISC-V

В учебных целях можно использовать специальную IDE для изучения ассемблера RISC-V под названием [RARS](https://github.com/thethirdone/rars).

Для ЦУ мы сделали свою сборку, которая умеет запускать отдельные функции, а не программу целиком: [RARS-CU](../../3rd-party/rars/). 

Для работы этой IDE требуется Java версии не ниже 21.

Запускается командой:
```
> java -jar rars-cu.jar
```

## Тулчейн для RISC-V программ 

Процесс сборки программ, предназначенных для другой процессорной архитектуры или операционной системы называется кросс-компиляцией.

Полные названия команд `gcc` имеют вид *триплетов*:

```
ARCH-OS[-VENDOR]-gcc
ARCH-OS[-VENDOR]-g++
ARCH-OS[-VENDOR]-gdb

и т. д.
```

где `ARCH` - это имя архитектуры: `i686`,  `x86_64`,  `riscv64`,  `aarch64`,  `ppc` и т.д.; `OS` - целевая операционная система, например `linux`, `win32` или `darwin`; а необязательный фрагмент триплета `VENDOR` - соглашения по бинарному интерфейсу, если их для платформы существует несколько, например для ARM это может быть `gnu` (стандартное соглашение Linux) или `none` (без операционной системы, просто голое железо).

В случае с Debian/Ubuntu можно установить окружение для работы с архитектурой RISC-V, установив пакеты:
 - `gcc-riscv64-linux-gnu` - компилятор gcc
 - `binutils-riscv64-linux-gnu` - базовый набор инструментов разработки
 - `qemu-system-riscv` - эмулятор процессора RISC-V
 - `qemu-user` - инструмент для запуска QEMU в текущем окружении
 - `gdb-multiarch` - поддержка кросс-платформенной отладки в gdb

Выполнение программ, предназначенных для других архитектур, возможно только интерпретацией инородного набора команд. Для этого предназначены специальные программы - эмуляторы.

Архитектуру `riscv64`, как и многие другие архитектуры, поддерживает эмулятор QEMU.

Эмулировать можно как компьютерную систему целиком, по аналогии с VirtualBox, так и только набор команд процессора, используя при этом окружение хост-системы Linux.

Команды QEMU имеют вид:

```
qemu-ARCH
qemu-system-ARCH
```

где ARCH - это имя эмулируемой архитектуры. Команды, в названии которых присутствует system, запускают эмуляцию компьютерной системы, и для их использования необходимо установить операционную систему.

Команды без system требуют в качестве обязательного аргумента имя выполняемого файла для ОС Linux, и эмулируют только набор команд процессора в пользовательском режиме, выполняя "инородный" исполняемых файл так, как будто это обычная программа.

Поскольку большинство программ, скомпилированных для Linux и другой процессорной архитектуры,, подразумевают использование стандартной библиотеки Си, необходимо использовать именно версию glibc для для нужной архитектуры. В Debian и Ubuntu они устанавливаются в `/usr/ARCH-OS-VENDOR/`.

Пример компиляции и запуска:

```
# Компилируем
> riscv64-linux-gnu-gcc -o program hello.c

# На выходе получаем исполняемый файл, который не запустится
> ./program
bash: ./program: cannot execute binary file: Exec format error

# Но мы можем запустить его с помощью qemu-riscv64
# Здесь параметр -L указывает, где искать библиотеки для riscv64
> qemu-riscv64 -L /usr/riscv64-linux-gnu ./program
Hello, World!

# Можно слинковать статически
> riscv64-linux-gnu-gcc -static -o program hello.c

# Тогда не нужно указыть путь до окружения riscv64:
# стандартная Си-библиотека уже внедрена в исполняемый файл
> qemu-riscv64 ./program
Hello, World!

```

У команд `qemu-*` предусмотрена возможность запуска в режиме отладки, - в этом случае возможно взаимодействие с `qemu` точно так же, как и с `gdbserver`:

```
# Компилируем с отладочной информацией
> riscv64-linux-gnu-gcc -static -g -o program hello.c
 
# Запускаем под qemu в режиме отладки
# Обратите внимание на опцию -g ПОРТ
> qemu-riscv64 -g 1234 ./program
 
# В другом терминале можно подключиться к программе из gdb
> gdb ./program
(gdb) target remote localhost 1234
```

## Ассемблирование

Как мы рассмотрели ранее, центральный процессор выполняет программу,
расположенную в оперативной памяти. Там же располагаются и данные для
обработки. Просто по значению числа в памяти нельзя сказать, чем
это число является - частью программы, целым числом, вещественным числом
или частью строки. Тип содержимого ячейки памяти определяется только
по тому, как она используется.

Программа начинает работать с какого-то начального состояния памяти.
Обычно в начале в памяти находится сама программа, которая не будет
в дальнейшем меняться, константы, используемые программой,
и глобальные переменные. В процессе работы программа может
использовать и другие ячейки памяти.

Таким образом, перед запуском программы необходимо подготовить
начальное состояние ОЗУ, в котором будут находиться инструкции
программы для выполнения на процессоре, значения констант
и начальные значения глобальных переменных. Эта задача возлагается
на программы ассемблера (assembler) и компоновщика (линкера) (linker).
Непосредственно загрузкой подготовленного образа памяти в память
занимается программа-загрузчик (loader).

Текстовый язык описания программы и данных для загрузки в
память называется языком ассемблера (assembly language).
Обычно, когда обсуждают язык ассемблера для определённого процессора,
фокусируются на текстовой форме записи инструкций, которые
исполняет процессор, то есть рассматривают систему команд,
виды регистров, способы адресации памяти &mdash;
что в совокупности составляет архитектуру набора команд
(ISA - instruction ser architecture).

В программе на языке ассемблера каждая инструкция процессора или
директива ассемблера записываются на отдельной строке.
Многострочные комментарии записываются с использованием `/*` ... `*/`,
а однострочные начинаются с `#`.

```asm
/*
 This is a multi-line comment
 */

# This is a single-line comment
```

По традиции каждая значимая строка ассемблерной программы имеет формат:

```txt
[LABEL:]OPCODE  [ARGUMENTS]...
```

Где `LABEL` — это необязательная _метка_, `OPCODE` — это либо директива ассемблера, либо _мнемоника_ инструкции процессора,
а `ARGUMENTS` — аргументы, которые разделяются запятыми. По традиции все `OPCODE` записываются начиная со столбца 9 строки, то есть
с отступом в один символ табуляции, равный 8 пробелам, а `ARGUMENTS` записываются начиная со столбца 17 (две табуляции по 8 пробелов).
Если метка слишком длинная и не помещается в отведённое для неё место, в строке записывается только она, а инструкция и её аргументы записываются в следующей строке.
Поэтому ассемблерная программа выглядит аккуратно выровненной по столбцам.

Инструкции процессора и большинство директив ассемблера размещают
закодированные инструкции данные по условному _текущему адресу_ в памяти и продвигают его
вперед на размер размещенных инструкций или данных. В программе на ассемблере
текущий адрес обозначается `.` (точка).

## Определение данных

Директивы определения данных формируют в памяти ячейки с заданными значениями.
Например,

```asm
        .byte   48, 49, 0x3a, 0b1000101, 046, 'x', -6
```

Эта директива размещает в памяти с текущего адреса 7 последовательных байт с указанными значениями.
Значения записываются по правилам языка C, то есть по умолчанию используется десятичная система, префикс `0x` означает
шестнадцатеричное значение, префикс `0` — восьмеричное, а в апострофах записываются символы (FIX) в кодировке ASCII.

__Внимание!__ Если просто написать `.byte` без последующих байтов, такая директива разместит в памяти __ноль__ байтов, то есть ничего.

Другие директивы определения данных перечислены в таблице.

| Директива | Что делает |
| --------- | ---------- |
| `.byte` | размещает в памяти 8-битные значения |
| `.half` | размещает в памяти 16-битные значения (по 2 байта подряд) |
| `.word` | размещает в памяти 32-битные значения (по 4 байта подряд) |
| `.dword` | размещает в памяти 64-битные значения (по 8 байт подряд) |
| `.float` | размещает в памяти значения IEEE 754 binary32 (по 4 байта подряд) |
| `.double` | размещает в памяти значения IEEE 754 binary64 (по 8 байтов подряд) |
| `.ascii` | размещает в памяти последовательность байтов, записанную по правилам строк в C без терминирующего `\0` |
| `.asciz` или `.string` | размещает в памяти последовательность байтов, записанную по правилам строк в C с терминирующим `\0` |
| `.zero` | размещает в памяти указанное число нулевых байтов |
| `.skip` | пропускает (резервирует) в памяти указанное число байтов (фактически то же самое, что `.zero`) |
| `.align` | выравнивает адрес по заданной степени числа 2 |

Сами по себе директивы размещения данных не выравнивают адреса, то есть директива `.word` вполне может
размещать данные по адресу, не кратному 4. Однако последующее использование данных по невыровненному адресу
как минимум даст штраф по времени выполнения, а как максимум — аварийное завершение программы.

Примеры:

```asm
        .byte   100
        .align  3               // выравнивание по 8 байтам
        .dword  0x200
        .double 1.885e12        // в .double и .float можно использовать запись с плавающей точкой
        .string "Hello", "world"
        .skip   128             // зарезервировать 128 байт
```

Как правило, risc-v инструменты настроены на работу с порядком байт Little Endian по умолчанию.
Поэтому директивые генерации многобайтных данных `.half`, `.word` и аналогичные генерируют байтовое представление чисел в порядке Little-Endian.
Спецификация архитектуры допускает работу и в Big-Endian, и в Little-Endian режиме, но чтобы скомпилировать программу под представление Big-Endian
потребуются дополнительные опции ассемблирования и компоновки.

## Метки

Метки — это символические имена для констант и адресов в памяти.
__Метки — это не переменные, а константы, их нельзя переопределять.__

Константное значение можно назначить метке с помощью директивы `.equ`.

```asm
        .equ    CHAR_BIT, 8
```

Эта директива назначает идентификатору `CHAR_BIT` значение 8. После этого в программе можно использовать `CHAR_BIT` везде, где можно использовать литеральное значение 8,
например, в директивах объявления данных.

Если метка определяется перед инструкцией в виде `LABEL:`, то значением метки является текущий адрес `.`.
Метка — это метаинформация, она как сущность не существует во время работы программы. Но метка
и её значение может присутствовать в таблице символов исполняемого файла.

Но сложность заключается в том, что абсолютный адрес в памяти, соответствующий логическому текущему
адресу, почти никогда не известен во время ассемблирования файла. Он может стать известным
при компоновке программы, когда будет известен полный набор объектных файлов, из которых компонуется
загружаемая программа, и будут заданы базовые адреса размещения в памяти. Либо даже абсолютный
адрес в памяти становится известным лишь при загрузке исполняемого файла на выполнение.
Если в данных и в кодировании инструкций используются не абсолютные адреса, а смещения
относительно текущей позиции, либо разности двух абсолютных адресов, такие данные и код называтся _позиционно-независимыми_
(position-independent). Такой код можно размещать по любому адресу в памяти, а может даже
и копировать во время выполнения программы. Если же в данных используются абсолютные адреса,
код называется _позиционно-зависимым_.

Например,

```asm
data:   .word   0x4433
        .align  3
        .dword  0xffeeddccbbaa9988
cur:
size:   .dword  cur-data              # ячейка, помеченная size, хранит значение cur-data, то есть размер (16)
```

но следующий фрагмент — позиционно-зависимый:

```asm
data:   .word   0x4433
        .align  3
        .dword  0xffeeddccbbaa9988
data_end:
range:  .dword  data, data_end
```

Если при ассемблировании программы, как правило, неизвестно, по какому адресу в памяти будут
размещаться инструкции и данные, как в итоге в памяти оказываются правильные адреса?
Это достигается с помощью _таблиц релокации_. На место ячеек памяти, в которых хранятся адреса,
ассемблер записывает нули, и в специальный раздел (секция релокаций) в объектном файле прописывает
в специальном формате, как изменяется значение ячейки памяти в зависимости от адреса размещения.
Конкретные правила кодирования информации определяются форматом исполняемого файла.
На Linux стандартный формат — ELF, на macOS — Mach-O, на Windows — PE.

В исполняемом файле релокации обычно отсутствуют. Если исполняемый файл настроен
на размещение в памяти по фиксированному адресу, то в ячейках памяти, требовавших релокации,
уже прописаны абсолютные адреса. Если же в память загружается перемещаемый исполняемый файл
или динамическая библиотека, для получения абсолютного адреса используется другая таблица,
подготовленная компоновщиком и модифицированная загрузчиком. В формате ELF она называется
GOT (global offset table).

### Локальные метки

GNU Toolchain для всех архитектур поддерживает _локальные метки_.
Область видимости локальной метки ограничена обычными метками, между которыми она расположена.
Локальная метка записывается как целое число.
Чтобы использовать значение локальной метки, нужно после числа, обозначающего метку,
написать `f`, если метка определена позже текущей точки программы, или `b`,
если метка определена до текущей точки программы. Например

```asm
data1:
        .byte   1
        .byte   1f-.    # смещение вперёд
        .byte   3
1:      .byte   4, 5
        .byte   1b-.    # смещение назад
        .byte   6, 7
data2:  .byte   8, 9
1:      .byte   10      # другая метка 1, предыдущая действует до data2
```

### Глобальные метки

Метки используются для связывания одного объектного файла с другими объектными
файлыми при компоновке программы. Объектные файлы могут быть получены из файлов
с исходным кодом на разных языках программирования.

По умолчанию метки имеют видимость только внутри одной единицы трансляции,
что соответствует ключевому слову `static` в программах на C. В программах
на ассемблере ограничение области видимости `static` действует по умолчанию,
явной директивы для этого нет. Если объявить метку _глобальной_ с помощью директивы

```asm
        .globl  LABEL
```

идентификатор `LABEL` будет помещён в _таблицу экспортов_ объектного файла,
полученного из данной единицы трансляции. Это значит, что этот идентификатор
будет доступен компоновщику, собирающему программу из нескольких единиц трансляции.
Другие единицы трансляции могут использовать эту метку у себя, и при компоновке
линкер настроит на правильный адрес `LABEL` все использования этой метки
во всех единицах трансляции.

Для использования метки из другой единицы трансляции не требуется предварительно
метку объявлять. Все идентификаторы, использованные в единице трансляции
программы на ассемблере, которые не являются какими-либо предопределёнными
идентификаторами и не объявлены в данной единице трансляции, считаются
глобальными метками, объявленными в другой единице трансляции.
Ассемблер помещает их в _таблицу импортов_ единици трансляции.
Компоновщик пытается найти каждый идентификатор из таблицы импорта
в таблицах экспорта других единиц трансляции. Если идентификатор из таблицы
импорта в них не найден, компоновка завершается с ошибкой.

## Связывание единиц трансляции на C и ассемблере

Компиляторы C обычно поддерживают различные расширения языка, которые позволяют
писать программу на ассемблере прямо внутри программы на C. Для gcc/clang
это конструкция `asm`, которую мы рассмотрим позже. И компилятор C позволяет получить
объектный файл, и ассемблер также выдаёт объектный файл, и эти файлы, написанные
на разных языках программирования, можно объединить в одну программу, чтобы единицы
трансляции могли использовать друг друга.

Компиляторы разных языков высокого уровня по-разному преобразуют индентификаторы,
используемые в программе, в идентификаторы в объектном файле. Например,
компилятор C++ использует сложный алгоритм _декорирования имён_ (name mangling),
в результате чего идентификатор в объектном файле содержит информацию
о пространстве имён, типах аргументов и т. д. Компиляторы C используют более простые схемы:

* В системах с форматом исполняемых файлов ELF идентификатор в программе на языке C не изменяется
  при трансляции в объектный файл.
* В macOS или Windows к идентификатору в программе на С приписывается символ подчёркивания.

Поэтому чтобы использовать идентификаторы из единицы трансляции на ассемблере в единице
трансляции на C достаточно в программе на C декларировать объект с правильным идентификатором
и типом, а в программе на ассемблере декларировать метку как глобальную.

В качестве примера рассмотрим единицу трансляции на C (`1.c`):

```c
#include <stdio.h>
int data1[4] = { 100, 200, 300, 400 }; // по умолчанию идентификаторы имеют external linkage, видимы из других единиц трансляции
extern int * const dataptr;            // идентификатор `dataptr` определён в другой единице трансляции
int main()
{
    for (int i = 0; i < 4; ++i) {
        printf("%d\n", dataptr[i]);
    }
}
```

и единицу трансляции на ассемблере (`2.s`):

```asm
        .globl  dataptr         # экспортируем метку dataptr
        .align  3               # выравниваем адрес
dataptr:
        .dword  data1           # data1 по умолчанию считается внешней
```

Скомпоновать две единицы трансляции в одну исполняемую программу можно следующей командой gcc.

```bash
gcc 1.c 2.s -o1
```

gcc самостоятельно выполнит компиляцию файла `1.c` на C в объектный файл, ассемблирование файла `2.s` и
финальную компоновку двух объектных файлов в исполняемую программу.

В программе на ассемблере определена метка `dataptr`. Это — адрес 8-байтовой ячейки в памяти, в которой
хранится адрес переменной `data1`. В терминах языка C — это глобальная переменная указательного типа
(`int *`). В единице компиляции `1.c` в объявлении `dataptr` используется ещё квалификатор `const`,
его наличие будет объяснено в следующем разделе.

## Секции

Возможностей, рассмотренных в предыдущих разделах, в целом достаточно чтобы писать простые программы из одной единицы
трансляции. Инструкции процессора мы можем разместить в начале файла, а данные для обработки — после инструкций.
Но при сборке многомодульных программ окажется, что в итоговом исполняемом файле инструкции процессора
и данные будут перемешаны. Это не очень правильно, так как мы хотим, чтобы и в итоговой программе
инструкции были в одном месте, а данные — в другом месте. Более того, в современных операционных системах код, константы
и данные размещаются в виртуальной памяти так, чтобы в работающей программе выполнялся _принцип минимальных привилегий_,
то есть не нужно давать больше возможностей, чем необходимо. Поэтому

* инструкции процессора размещаются в виртуальной памяти, к которой разрешён доступ только на чтение и выполнение (`r-x`), но запрещена запись,
* константы, используемые в программе, размещаются в памяти, к которой разрешён доступ только на чтение (`r--`),
* а глобальные переменные — в памяти, к которой разрешён доступ только на чтение и запись (`rw-`), но запрещено выполнение инструкций.

Тем важнее собирать однородную информацию (код, константы, переменные) в одном месте.
В программе на языке ассемблера для группировки информации используются _секции_.
Все современные архитектуры имеют очень похожий набор стандартных секций. А три секции (`.text`, `.data`, `.bss`)
поддерживаются с начала 70-х готов с первых версий Unix.

Типичный набор секций рассмотрим далее.

Секция `.text` предназначена для размещения инструкций процессора (исполняемого кода). В секции `.text` размещаются
скомпилированные тела функций программы на C и используемых библиотек. Исторически в секции `.text` размещались
и константы, определённые в программе, но в настоящее время для них используются отдельные секции.
Содержимое секции `.text` загружается в оперативную память с правами
на чтение и исполнение, таким образом исполняемая программа не может случайно или намеренно испортить
исполняющийся код. Секция `.text` является активной в начале программы на ассемблере, поэтому все наши
фрагменты программ на ассемблере выше в тексте размещали данные (по сути это константы) в секции `.text`.

Секция `.data` предназначена для размещения глобальных переменных. Они могут инициализироваться произвольным значением,
как описано выше.

Секция `.bss` предназначена для размещения глобальных переменных, инициализированных нулём. Данные, размещаемые в секции
`.bss` не занимают место в исполняемом файле, а необходимая память аллоцируется ядром операционной системы
при загрузке исполняемого образа в память. 

Секция `.rodata` в современных операционных системах используется для размещения константных данных.
Ячейки памяти в этой секции можно только считывать, но не записывать или исполнять программу, размещённую в них.
Эта секция используется и на x86, и на ARM, и на RISC-V.

Сводная таблица использования секций приведена в таблице ниже.

| Название секции | Директива ассемблера | Назначение |
| --------------- | -------------------- | ---------- |
| `.text`         | `.text`              | Код программы — инструкции процессора |
| `.rodata`       | `.section .rodata`   | Константные данные, в том числе таблицы переходов для switch или виртуальных функций |
| `.data`         | `.data`              | Глобальные переменные, инициализируемые не нулём |
| `.bss`          | `.bss`               | Глобальные переменные, инициализируемые нулём |

Дополнительно в программе могут определяться и другие секции. Например, компилятор C++ помещяет тело
каждой инстанциированной шаблонной функции в отдельную секцию. При компоновке линкер оставляет в исполняемом файле
только один экземпляр инстанциированной шаблонной функции из всех, которые находились в обработанных объектных файлах.

Каждая секция обладает своим счётчиком текущего положения `.` (точка), поэтому после переключения в другую секцию,
данные либо инструкции будут добавляться в её конец.

При компоновке итоговой исполняемой программы линкер объединяет одноимённые секции из всех компонуемых объектных
файлов, включая объектные файлы, извлечённые из статических библиотек, и записывает их в исполняемый файл.
Обычный порядок размещения секций в исполняемом файле: `.text` — `.rodata` — `.data` — `.bss`.

Отличие секции `.data` от секции `.bss` можно продемонстрировать на следующем примере:

Следующий файл на языке ассемблера:

```asm
        .data
arr:    .skip   1024*1024
```

породит объектный файл размером 1049464 байт, который при финальной компоновке добавит 1 MiB к размеру
исполняемого файла. В то время как файл:

```asm
        .bss
arr:    .skip   1024*1024
```

породит объектный файл размером 40 байт, который при компоновке исполняемой программы не увеличит её размер.
Лишь при загрузке исполняемой программы в память перед запуском ядро операционной системы выделит программе
1 MiB памяти.

## Instruction Set Architecture (ISA)

Когда говорят о центральных процессорах в различных устройствах,
от пылесосов до высокопроизводительных серверов, редко когда
детализация доходит до конкретной модели, серийного номера и т. п.
Спецификация процессора может быть достаточно общей,
например, Intel Core i7 или Apple silicon M4. На обывательском
уровне известно, что процессоры Intel и AMD совместимы
по программному обеспечению, а процессоры Intel и Apple silicon — нет,
то есть программа для одного процессора не запустится просто так,
без специальных вспомогательных программ на другом процессоре.

Технически правильно говорить, что те или иные процессоры
реализует одну или разную _архитектуру системы команд_ (instruction
set architecture). Разные процессоры с одной архитектурой системы
команд, например Intel Core i7 и AMD Ryzen практически полностью
совместимы друг с другом, но вообще не совместимы с процессорами
с другой архитектурой системы команд.

_Архитектура системы команд_ — это абстрактная модель, определяющая
программируемый интерфейс центрального процессора компьютера.
Эта модель определяет, как программное обеспечение взаимодействует
с аппаратурой. Можно сказать, что архитектура системы команд
— это спецификация API для выполнения кода наподобии OpenAPI спецификаций для
клиент-серверного взаимодействия.

В архитектуру системы команд входят следующие составные части:

* Какие операции может выполнять процессор — набор инструкций. Все процессоры могут выполнять инструкции
  сложения, вычитания, сдвигов, битовых операций, но, например умножение или деление могут отсутствовать.
* Обработка каких типов данных поддерживается в системе команд. Например, поддерживаются ли типы
  с плавающей точкой или векторные типы.
* Как устроена специальная супер-быстрая память в процессорном ядре (_регистры_ процессора).
  Какие имеются особенности использования регистров в инструкциях.
* Какими способами инструкции процессора могут задавать адреса оперативной памяти для выполнения операции
  (_режимы адресации_).
* Какие требования накладываются на состояние ячеек памяти при одновременном доступе из нескольких ядер
  (_модель памяти_).

Полное описание архитектуры системы команд современных процессоров занимает несколько тысяч страниц текста.
В рамках данного курса мы можем затронуть только самые базовые моменты.

## RISC и CISC архитектуры

Имя архитектуры системы команд `RISC-V` можно понимать как
«Архитектура RISC, 5 поколение». Акроним `RISC` сам по себе обозначает
Reduced Instruction Set Computer, то есть компьютер с сокращённым
набором инструкций.

Архитектура RISC возникла как ответ на «вызов времени». В 70-х
и начале 80-х годов происходил переход от программ, написанных на языке ассемблера
к программам на языках высокого уровня. Качество машинного кода, генерируемого
компиляторами, росло; массово распространялись переносимые
операционные системы и языки программирования; появились первые, пока ещё
простые микропроцессоры. Но в компьютерах тех лет, таких как IBM 360 или DEC VAX
были реализованы очень большие и сложные наборы машинных инструкций,
«дружественных» к человеку. Например, в наборе инструкций VAX присутствовали
инструкции работы с двусвязными списками.

Оказалось, что компиляторы в скомпилированной программе используют
намного меньше инструкций и режимов адресации памяти, чем заложено разработчиками
в наборе инструкций, то есть существенная часть аппаратуры компьютера
просто не используется. Авторы RISC архитектуры
(в частности, David Patterson, один из авторов RISC-V)
назвали традиционный подход CISC (Complex Instruction Set Computer) и, разрабатывая новую архитектуру,
ставили перед собой такие цели:

* ориентировать систему команд процессора на компиляторы, а не на человека, убрав из системы команд то, что компиляторами не используется;
* упростить формат представления инструкций в памяти.

Обычно к особенностями архитектуры RISC относят следующее:
* большое (относительно CISC) количество регистров общего назначения;
* фиксированная длина инструкции;
* команды обработки данных берут аргументы операций из регистров и сохраняют результат в регистр, который указывается явно.

Например, у процессора Intel i386 (CISC) всего 8 регистров общего назначения, а у его ровестника ARM32 &mdash; 16.
У процессоров семейства Intel x86 одна инструкция процессора в закодированном виде может иметь длину от 1 до 15 байт,
а у процессоров ARM и RISC-V &mdash; 4 байта. У процессоров Intel x86 у операции сложения два аргумента, и один из аргументов
является и результатом операции, кроме того один из аргументов может задавать адрес в памяти программы, в то время как у
процессоров ARM и RISC-V операция сложения требует три аргумента, первый из которых &mdash; регистр-результат, а два других &mdash; регистры, значения которых складываются.

В итоге процессоры на архитектуре RISC обладают, как правило, намного меньшим энергопотреблением на единицу производительности.
Во многих случаях они могут работать без активного отвода тепла от процессора (кулера). Поэтому процессоры RISC стали доминировать
на мобильных устройствах.

Для написания программ для архитектуры RISC-V можно использовать множество языков &mdash; С, С++, Java, Python, C# и т.д.
Однако лучшим способом разобраться в том, как работает та или иная архитектура, глубже ее понять позволяет
программирование непосредственно на языке ассемблера. В повседневной практике программирование на уровне языка ассемблера
или чтение/анализ программ на ассемблере требуется у достаточно узкого класса специалистов: разработчики операционных
систем и компиляторов языков программирования, разработчики или аналитики средств компьютерной безопасности,
но иметь общее понимание того, как работает центральный процессор компьютера, полезно всем.

## ISA RISC-V

Архитектура системы команд RISC-V разработана в Калифорнийском университете Беркли
(the University of California, Berkeley). Это — пятое поколение исследовательских
архитектур RISC, отсюда и название RISC-V. David Patterson, один из авторов серии
RISC опубликовал архитектуру RISC-I впервые в 1981 году, когда и был
предложен термин RISC. Все технические документы опубликованы под
_свободными лицензиями_ (сначала BSD, потом Creative Commons).
Любое использование спецификаций, программного кода и прочего
не требует лицензионных отчислений, поэтому архитектура системы команд
получила популярность в микроконтроллерах — простых микропроцессорных устройствах,
устанавливаемых в различное оборудование от бытового (например чайники)
до промышленного.

Архитектура построена по модульному принципу. Есть несколько базовых наборов,
в которых специфицирован минимальный набор инструкций, тем не менее достаточный
для полноценного процессора.

| Обозначение | Описание | Число инструкций |
| - | - | - |
| RV32I | Базовые инструкции: 32 бита, 32 регистра | 40 |
| RV32E | Базовые инструкции для встраеваемых систем (embedded): 32 бита, 16 регистров | 40 |
| RV64I | Базовые инструкции: 64 бита, 32 регистра | 52 |
| RV64E | Базовые инструкции для встраеваемых систем (embedded): 64 бита, 16 регистров | 52 |
| RV128I | Базовые инструкции: 128 битов, 32 регистра | 64 |

В базовые наборы не входят инструкции умножения, деления, атомарной работы
с памятью, работы с плавающей точкой, векторные инструкции и т. д.
Некоторые расширения перечислены ниже:

| Обозначение | Описание | Число инструкций |
| - | - | - |
| M | Целочисленное умножение и деление | 13 (RV64) |
| A | Атомарный доступ к памяти | 22 (RV64) |
| F | Плавающая точка binary32 | 30 (RV64) |
| D | Плавающая точка binary64 | 32 (RV64) |

При компиляции программы под RISC-V в исполняемый файл в формате ELF
записывается специальная секция, содержащая строку, кодирующую
базовый набор инструкций и расширения, для которых скомпилирована программа.
Эту строку можно получить с помощью команды `readelf -A`
или `riscv64-linux-gnu-readelf -A`

```bash
readelf -A program
```

Вывод будет примерно таким:

```text
Attribute Section: riscv
File Attributes
  Tag_RISCV_arch: "rv64i2p1_m2p0_a2p1_f2p2_d2p2_zicsr2p0_zifencei2p0_zmmul1p0_zaamo1p0_zalrsc1p0"
```

Тег разбивается на части символом подчёркивания. Буква `p` в `2p1` означает десятичную
точку, то есть декодируется как `2.1`. Данная строка декодируется следующим образом:

| Компонент строки | Описание | Версия спецификации |
| - | - | - |
| `rv64i2p1` | Базовый 64-битный набор инструкций | 2.1 |
| `m2p0` | Целочисленное умножение и деление | 2.0 |
| `a2p1` | Атомарная работа с памятью | 2.1 |
| `f2p2` | binary32 floating point | 2.2 |
| `d2p2` | binary64 floating point | 2.2 |
| `zicsr2p0` | Управляющие регистры (CSR) | 2.0 |
| `zifencei2p0` | Барьеры чтения инструкций из памяти | 2.0 |
| `zmmul1p0` | Только умножение, без деления в расширении M | 1.0 |
| `zaamo1p0` | Подмножество A для read-modify-write доступа | 1.0 |
| `zalrsc1p0` | Подмножество A Load-Reserve/Store-Conditional | 1.0 |

Несмотря на то, что `zmmul1p0` выделено отдельно, данный процессор полностью
поддерживает и инструкции деления, так как они специфицированы в `m2p0`.
Если удалить избыточные компоненты тег можно сократить до
`rv64imafd_zicsr_zifencei`, который в итоге имеет стандартное обозначение `rv64g`
(general purpose application 64-bit RISC-V ISA).

В совокупности это базовый набор инструкций и расширения для 64-битного
процессора, на котором работает операционная система Linux.
Небольшое количество инструкций из этого набора инструкций мы будем

## Регистры процессора

Регистры — это небольшое число специальных ячеек памяти, расположенных
непосредственно в самом ядре процессора. Из регистров процессора берутся
аргументы для выполнения вычислительных операций, и в регистр процессора
сохраняется результат. Регистры процессора хранят адреса для загрузки
значения из памяти или сохранения значения в память.

Кроме того, в регистрах процессора передаются аргументы функций
и возвращаются результаты работы функций при вызове функций языков высокого уровня.
При вызове функции, написанной на ассемблере, из программы на C
компилятор C поместит аргументы в регистры, а после возврата из
функции компилятор переместит результат из регистра возвращаемого значения.

Поскольку регистров ограниченное количество их может не хватить
в сложных программах или для вычисления сложных выражений. Тогда для хранения
значений используется стек, и компилятор C генерирует перемещение значений
из регистров в стековую память (register spill) и обратно.
Одни и те же регистры переиспользуются во вложенных цепочках вызовов,
поэтому важна дисциплина использования регистров при вызовах функций.
Дисциплина использования регистров является частью _Application Binary Interface_ (ABI),
то есть соглашений о взаимодействии компонентов программы на уровне
бинарного кода.

Рассмотрим две функции: одна функция (caller) вызывает другую функцию (callee).
Обе функции используют один и тот же набор регистров, поэтому вызванная функция
при неправильном использовании может испортить значения в регистрах,
которые используются вызываемой функцией для работы.
Регистры процессора делятся на две группы:

* __callee-saved__. Регистры, за сохранность значения которых отвечает
  та функция, которую вызвали (callee). Это значит, что при возврате
  из вызванной функции вызывающая функция может быть уверена, что в
  callee-saved регистрах будет находиться то же самое значение,
  что и в момент вызова функции.
*__caller-saved__. Регистры, сохранность которых после возврата из
  вызванной функции не гарантируется. Если необходимо, чтобы значение
  такого регистра сохранилось неизменным после возврата из функции,
  вызывающая функция (caller) должна сохранить значение регистра.

Регистры в программе на ассемблере обозначаются `x0` — `x31`.
Для регистров существуют альтернативные имена, которые отражают
назнечение регистров, и в программах обычно используются альтернативные имена.
Ниже дана таблица, описывающая регистры.

| Имя | Альт. имя | caller/callee saved | Описание |
| - | - | - | - |
| `x0` | `zero` | — | Чтение из регистра всегда даёт 0, запись игнорируется. |
| `x1` | `ra` | caller | Хранит адрес инструкции, на который должен выполниться переход, при завершении текущей функции |
| `x2` | `sp` | callee | Адрес верхушки стека |
| `x3` | `gp` | — | Содержит адрес глобальных данных программы. Не изменяется во время исполнения программы |
| `x4` | `tp` | — | Хранит адрес thread-local блока |
| `x5` | `t0` | caller | Временное хранение аргументов операций |
| `x6`, `x7` | `t1`, `t2` | caller | Временное хранение аргументов операций |
| `x8` | `s0` или `fp` | callee | Хранение локальных переменных, аргументов операций или frame pointer |
| `x9` | `s1` | callee | Хранение локальных переменных, аргументов операций |
| `x10`–`x11` | `a0`–`a1` | caller | Параметры функции, возвращаемые значение, временное хранение аргументов. |
| `x12`–`x17` | `a2`–`a7` | caller | Параметры функции, временное хранение аргументов инструкций. |
| `x18`–`x27` | `s2`–`s11` | callee | Хранение локальных переменных, аргументов операций |
| `x28`–`x31` | `t3`–`t6` | caller | Временное хранение аргументов операций |

Отличие регистров серии `t` от регистров серии `s` в том, что значние `t`-регистра
теряется при любом вызове функции. Специальное назначение регистров `ra`, `sp`
мы подробнее расмотрим в следующем занятии.

В отличие от
других архитектур не существует отдельных обозначений для частей регистров.
Например, на ARM64 регистр `W0` является младшими 32 битами регистра `X0`.
В архитектуре RISC-V работа с частями регистра реализуется
отдельными инструкциями процессора. Когда инструкция работает с 32-битными
частями регистров при сохранении значения в 64-битный регистр
по умолчанию выполняется расширение знака. Таким образом регистры рассматриваются
как переменные знакового типа `int64_t`. В других архитектурах старшие 64 бита
обнуляются.

## Функция сложения двух чисел

Предположим, что мы хотим написать функцию с прототипом

```c
long long sum(long long a, long long b);
```

Компилятор языка C при вызове функции `sum` поместит аргумент `a` в регистр `a0`,
а аргумент `b` в регистр `a1`. Наша функция должна вернуть результат в `a0`.

```asm
        .globl  sum
sum:    add     a0, a0, a1
        ret
```

Инструкция `ret` завершает выполнение функции и возвращает управление
в вызвавшую нас функцию. Подробнее о механизме вызова функций и возврата
из них мы будем говорить в следующем занятии.
Внутри нашей функции мы можем как угодно
менять значения регистров `a0`...`a7` и `t0`...`t6`.

Предположим теперь, что мы хотим выполнить операции над 32-битными числами:

```
unsigned sum32(unsigned a, unsigned b);
```

Компилятор языка C поместит аргумент `a` в младшие 32 бита регистра `a0`
и аргумент `b` в младшие 32 бита регистра `a1`. Функция должна вернуть
результат в младших 32 битах регистра `a0`.

```asm
        .globl  sum
sum:    addw    a0, a0, a1
        ret
```

Инструкция `addw` выполнит расширение знака 32 младших бит результата на
старшие 32 бита в `a0`, но нам это не важно, так как в результате
требуются младшие 32 бита.

## Сложение и умножение

Предположим, что мы хотим написать функцию с прототипом

```c
long long poly(long long a, long long b, long long c, long long d, long long x);
```

Функция должна вычислить выражение `a*x*x*x+b*x*x+c*x+d`.

Компилятор поместит аргументы функции в регистры `a0`, `a1`, `a2`, `a3`, `a4`.
Результат нужно вернуть в `a0`.

Напишем простой (неэффективный) вариант умножения.

```asm
        .globl  poly
poly:   mul     t0, a4, a4
        mul     t0, t0, a4
        mul     t1, a0, t0
        mul     t0, a4, a4
        mul     t0, t0, a1
        add     t1, t1, t0
        mul     t0, a2, a4
        add     t1, t1, t0
        add     t1, t1, a3
        mv      a0, t1
        ret
```

Количество инструкций в этой функции можно существенно сократить.
